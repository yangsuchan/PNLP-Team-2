## 1. 프로젝트 요약과 제안서에서 바뀐 점

### 1.1 연구 주제
**ThinkEnough: Hidden-State Probing for Dynamic Early Exit in 3D-LLMs**

- 고정된(frozen) 추론 모델이 생각(CoT)하는 도중에, 그 모델의 hidden state에 가벼운 probe(작은 분류기)를 붙인다.
- probe는 각 지점에서 **"지금까지 생각한 것으로 정답을 내기에 충분한가?"** 를 예측한다. 충분하면 STOP, 아니면 CONTINUE.
- 충분하다고 판단하면 생각을 일찍 끝내서 **토큰과 시간을 아낀다.**
- 다른 연구와의 차이:
  - ReProbe는 "지금 단계가 맞는가"를 예측하지만, 우리는 "답하기에 **충분한가**"를 예측한다.
  - DEER는 생각 도중 시험 삼아 답을 생성해 보고(trial answer) 멈출지 정하지만, 우리는 **시험 답을 생성하지 않고** hidden state만 본다.

### 1.2 연구 질문
1. 3D 공간 추론에서 문제마다 다른 "멈춰도 되는 지점"이 존재하는가?
2. hidden state에 "충분함"에 대한 정보가 담겨 있는가?
3. probe로 멈추면 정확도를 지키면서 토큰과 latency를 줄일 수 있는가?

### 1.3 제안서에서 바뀐 점

| 항목 | 원래 제안서 | 현재 |
|---|---|---|
| CoT 길이 | Short CoT (SCoT, 약 100토큰) | **Long CoT** |
| 메인 모델 | SCoT-Reasoner | **Qwen3-8B thinking** |
| 3D 장면 입력 | 3D 모델이 직접 입력받음 | Qwen3는 텍스트만 받으므로 **ScanRefer 캡션 문장**으로 장면을 설명 |
| 데이터 | SCoT 위주 | **SQA3D가 주력** (Train/Val/Test, 정확도 평가), SCoT는 보조 |
| GPU | RTX 4090 24GB 가정 | RTX 5080 **16GB** → Qwen3-8B는 양자화(4-bit/8-bit) 필요 💭 |

### 1.4 비교할 방식과 지표 (제안서 기준)
- **방식**: Direct Answer(생각 없이 바로 답), Fixed-k(정해진 k단계만 생각), Fixed Token Budget(정해진 토큰만큼만 생각), Full Long CoT(끝까지 생각), **Probe Early Exit(우리 방법)**, DEER 방식, Oracle(정답을 알고 가장 이른 지점에서 멈추는 상한선)
- **지표**: 정확도(EM이 주 지표), Performance Retention, Accuracy Difference, 추론 토큰 감소율, Latency, Probe AUROC/AP/Precision/Recall/F1

## 2. 전체 파이프라인과 역할 분담

```
SQA3D 원본
  │ ① 조사 (D&E)                         ← 완료, 실제 데이터
  │ ② 전처리 · 분할 · Pilot (D&E)          ← 완료, 실제 데이터
  ▼
[A] Qwen3로 Full Long CoT 생성           ← 아직 안 함 (GPU)
  │ ③ CoT를 checkpoint로 자르기 (D&E)     ← 코드 완료, 가상 데이터로 검증
  ▼
[A] checkpoint마다 강제로 답 내게 하기     ← 아직 안 함 (GPU)
  │ ④ STOP/CONTINUE 라벨 만들기 (D&E)     ← 코드 완료, 가상 데이터로 검증
  ▼
[A] hidden state 추출 → probe 학습 → 예측  ← 아직 안 함 (GPU)
  │ ⑤ τ 선정, 방식 비교, 평가 (D&E)        ← 코드 완료, 가상 데이터로 검증
  ▼
[A] 온라인 Early Exit 실행, latency 측정   ← 아직 안 함 (GPU)
  │ ⑤ 최종 결과표 (D&E)
```

**역할 정리**

| 담당 | 맡은 일 |
|---|---|
| **Dataset & Evaluation (D&E, 나)** | 데이터 조사·전처리·분할, 장면 텍스트화, checkpoint 분할, 답 추출·채점, 라벨링, 지표 계산, τ 선정, 결과표 |
| **모델 담당 A** | Qwen3 설정·실행(GPU), Full CoT 생성, 강제 답변 생성, hidden state 추출, probe 학습, 온라인 Early Exit, latency 측정 |

정리하면 D&E는 **데이터를 준비하고 "채점하는 쪽"** 을 맡고, 그 사이에서 **모델을 돌리는 일은 A 담당**이다. 그래서 ③④⑤가 실제 데이터로 돌아가려면 A의 출력이 필요하다.

## 3. 작업 보고 ① SQA3D 데이터 조사 (실제 데이터)

**목적**: 쓸 데이터가 어떻게 생겼는지, 함정은 없는지 실험 전에 확인한다.

### 3.1 한 일과 결과

- 공식 자료(GitHub, Zenodo, 논문)를 확인하고 필요한 파일만 받았다. 질문·정답 `sqa_task.zip`(4.6MB)과 캡션 pkl 파일이다. 이미지(BEV)와 비디오는 텍스트 모델에 필요 없어서 받지 않았다. 🔍 md5가 공식값과 같다.
- ✅ 라이선스: 데이터 CC-BY-4.0, 코드 Apache

**공식 분할** 🔍

| split | 질문 수 | 장면 수 | 고유 정답 수 |
|---|---:|---:|---:|
| train | 26,623 | 518 | 1,277 |
| val | 3,261 | 65 | 396 |
| test | 3,519 | 67 | 403 |
| 합계 | 33,403 | 650 | |

- 🔍 분할 사이에 **장면이 하나도 겹치지 않는다.** 같은 방을 보고 학습하고 평가하는 누출이 없다. 따라서 우리가 데이터를 새로 나눌 필요가 없다.
- 🔍 **Test 정답이 공개되어 있다.** 그래서 "튜닝(프롬프트, τ, probe 구조 선택)은 val로만 하고 test는 마지막에 한 번만 쓴다"는 규칙이 꼭 필요하다.

**정답 분포** 🔍
- 정답의 92.7%가 한 단어다. 상위 정답은 yes, no, right, left, one, two 등이다.
- 질문 첫 단어: What 30.7%, Is 19.0%, How 15.1%, Can 9.5%, Which 8.5%
- train에서 가장 많은 정답 "yes"만 찍어도 val 9.3%, test 10.9%가 나온다.

**공식 채점 방식의 문제** ✅🔍
- 공식 LLM 채점은 예측을 정규화한 뒤, 완전 일치나 부분 문자열이 아니어도 **단어가 하나만 겹치면 정답**으로 친다. 예: 정답 "left side"에 예측 "right side"도 정답이 된다.
- **빈 예측도 정답**으로 처리된다(빈 문자열은 모든 문자열의 부분 문자열이라서).
- 원저자도 "a bit aggressive"하다고 인정했다 ✅.
- 우리 연구에서는 라벨이 채점 결과로 정해진다. 채점이 느슨하면 STOP 라벨이 실제보다 일찍 붙는다. 그래서 **정규화 EM(정규화 후 완전 일치)을 주 지표**로 쓰기로 했다.

**참고 기준선** ✅ (SQA3D 리더보드, test)

| 방식 | 정확도 |
|---|---:|
| GPT-3 + ScanRefer 캡션 | 41.00 |
| Blind test (3D 정보 없음) | 43.65 |
| ScanQA | 46.58 |
| 사람 | 90.06 |

- 💭 3D 정보 없이 푼 Blind가 ScanQA와 차이가 크지 않다. 질문 문장이 분할 사이에 약 24% 겹치고 정답이 치우쳐 있어서, **언어 사전지식만으로도 점수가 꽤 나온다.** 그래서 "캡션 없이 질문만 주는 기준선"을 넣어야 캡션이 정말 도움이 되는지 보일 수 있다(9.3절 #18).

**기타 위험 요소**
- 🔍 라벨 노이즈: 위치·방향까지 똑같은 문항인데 정답이 다른 경우가 5건 있다(train 3, val 1, test 1).
- 💭 사전학습 오염: SQA3D는 2022~2023년부터 test 정답까지 공개되어 있어서, Qwen3가 학습 중에 봤을 가능성을 배제할 수 없다. 검증할 방법이 없다.
- ⚠️ `position`/`rotation`(에이전트의 실제 위치·방향)을 프롬프트에 넣으면 리더보드 기준으로 다른 설정이 된다. 기본적으로 넣지 않는다.

📄 자세히: `docs/dataset_audit.md`

## 4. 작업 보고 ② 전처리, Train/Val/Test, Pilot (실제 데이터)

**목적**: 모델에 바로 넣을 수 있는 깔끔한 입력 파일을 만든다.

### 4.1 레코드 구조
한 문항 = 한 줄(JSONL). **모델 입력과 정답을 분리**했다.

```jsonc
{
  "question_id": 220602000182,
  "split": "test",
  "input": {               // ← Qwen3에 들어가는 것은 이 안의 값뿐
    "scene_id": "scene0607_00",
    "situation": "I am facing the paper towel dispenser ...",
    "question": "What color is the refrigerator on my right?",
    "scene_captions": [{"object": "chair", "caption": "this chair is facing left. it is brown."}, ...]
  },
  "reference_answers": ["brown"],   // ← 채점 전용
  "meta": { ... flags, 토큰 수, position/rotation(공식 채점 키 용도로만) ... },
  "source": { ... 원본 파일, md5, seed ... }
}
```

### 4.2 장면을 텍스트로 바꾸기
- Qwen3-8B는 3D 장면을 직접 볼 수 없다. 그래서 공식 LLM 평가 방식처럼 **ScanRefer 캡션**(물체를 설명하는 문장, 예: "a black tv ... on the right side of the blue curtain")을 넣는다.
- 공식 코드는 seed 없이 문항마다 무작위로 30개를 뽑는다. 우리는 재현할 수 있도록 **장면마다 고정 seed(`"42:<scene_id>"`)로 30개를 뽑고 원래 순서를 유지**했다. 같은 장면의 모든 질문에 똑같은 캡션이 들어간다.
- 🔍 ScanRefer 캡션은 test 장면 100%, train 99.8%, val 98.5%를 덮는다.

### 4.3 데이터 개수
- 전체 전처리본: **문항을 하나도 지우지 않았다** (train 26,623 / val 3,261 / test 3,519). 문제가 있는 문항은 `meta.flags`로 표시만 했다.
- **Pilot** (작게 먼저 실험해 보기 위한 부분집합, seed 42)

| split | 추출 | 장면 수 | 제외한 것 |
|---|---:|---:|---|
| train | 300 | 223 | 캡션 누락, 라벨 충돌, 중복 질문 |
| validation | 100 | 47 | 〃 |
| test | 100 | 53 | 〃 |

- Pilot은 (질문 유형 × 정답 유형)으로 층화해서 뽑았다. 🔍 질문 유형과 정답 유형 비율이 전체 데이터와 거의 같다(예: what 30.7% → pilot 30.7%).

### 4.4 입력 길이 🔍 (Qwen3-8B tokenizer, CPU에서만 사용)

| split | 전체 입력 토큰 (중앙값 / p95 / 최대) |
|---|---|
| train | 693 / 838 / 1,141 |
| validation | 683 / 851 / 1,091 |
| test | 700 / 843 / 998 |

- 입력은 약 1.1k 토큰 이하다. 💭 메모리 부담은 대부분 Long CoT **출력** 쪽에서 생길 것이다.
- 이 토큰 수는 **임시 프롬프트 템플릿**(`sqa3d_official_gpt_v0`, 공식 GPT 프롬프트 + 1-shot 예시) 기준이다. 프롬프트가 바뀌면 다시 센다.

### 4.5 발견한 문제 (표시만 하고 고치지 않음)

| 문제 | 내용 |
|---|---|
| 캡션 없는 장면 | train `scene0546_00`(50문항, 0.19%), val `scene0217_00`(49문항, 1.50%). test는 없음 |
| 라벨 충돌 5건 | 예: test `scene0100_00` "What color is the bathtub?" → `backward` / `brown` (다른 질문의 정답이 섞인 것으로 보임) |
| 중복 질문 | 정답까지 같은 중복: train 13그룹, val 1그룹, test 2그룹 |

### 4.6 검증
- 🔍 **검증 59개 항목 모두 통과**: 개수 일치, question_id 유일, 분할 간 장면 중복 0, 정답 누락 0 등

- 🔍 두 번 실행한 결과 파일의 md5가 같다(재현 가능).

### 4.7 채점기

- 공식 채점에서 빈 답을 오답으로 치는 옵션(`empty_pred_is_wrong`)도 만들어 두었다.

| 예측 | 정답 | 공식 | EM |

## 5. 작업 보고 ③ Reasoning Checkpoint (가상 데이터로만 검증)

**목적**: Qwen3가 쓴 긴 생각(`<think> ... </think>`)을 **"여기서 멈출 수 있는 지점"(checkpoint)** 들로 자른다. 각 지점까지의 누적 생각(prefix)이 강제 답변과 hidden state 추출의 기준이 된다.

### 5.1 처리 흐름
```
생성 결과 1개
 ├─ ① <think> 파싱: 생각 부분과 최종 답 분리
 ├─ ② 분할기: 생각을 조각으로 자름
 ├─ ③ checkpoint 생성: checkpoint 0(생각 없음) + 조각마다 1개, 누적 prefix
 └─ ④ 토큰 위치 계산: 원본 생성 토큰 ID가 있을 때만, 없으면 null
```

### 5.2 `<think>` 파싱
출력 형식이 이상해도 멈추지 않고 상태를 기록한다.

| 출력 모양 | 상태 |
|---|---|
| `<think> 생각 </think> 답` | `ok` |
| `생각 </think> 답` | `missing_open_tag` (`<think>`가 프롬프트 쪽에 들어가는 모델이면 이렇게 됨) |
| `<think> 생각` (잘림) | `unclosed_think` |
| `답` (태그 없음) | `no_think_tags` |
| `<think> </think> 답` | `empty_reasoning` |
| 빈 출력 | `empty_output` |

### 5.3 분할기 3가지
- **sentence (기본)**: `. ! ?` 뒤 공백, 줄바꿈에서 자른다. 소수점(`3.5 m`), 약어(`e.g.`, `approx.`), 줄 앞 번호(`1.`)에서는 자르지 않는다.
- **line**: 줄바꿈마다
- **numbered_step**: `1.`, `2)`, `Step 3:`, `- ` 같은 단계 표시 앞에서
- 모든 조각을 이어 붙이면 **원본과 글자 하나까지 똑같다**(테스트로 확인).
- 새 분할 방식(예: "Wait," 기준)을 추가할 자리를 마련해 두었다.

### 5.4 Checkpoint 0
- "생각을 하나도 안 한 상태"다. 제안서의 Depth 0 / Direct Answer 기준선과 맞춘 것이다.

### 5.5 토큰 위치와 hidden state 위치
- `checkpoint_id = {run_id}/{question_id}/{segmenter}/{index}`. 강제 답변, 라벨, probe 예측을 이 값으로 연결한다.
- probe는 각 checkpoint의 **마지막 토큰 위치의 hidden state**를 읽어야 한다.
  `hidden_state_position = prompt_token_count + reasoning_token_end - 1`
- **발견하고 고친 문제**: Qwen3 tokenizer는 공백을 다음 단어에 붙인다(`' So'`가 한 토큰). 처음에는 checkpoint의 마지막 토큰이 다음 문장의 `' So'`가 되어, 다음 문장을 조금 본 위치에서 hidden state를 꺼내는 문제가 있었다. → **공백을 뺀 prefix 끝**을 기준으로 정렬하도록 고쳤다.
- Qwen3는 `.\n\n`을 한 토큰으로 만들기도 해서, 이런 경우는 `exact_up_to_whitespace`로 표시한다.
- 원본 생성 토큰 ID가 없으면 위치를 **지어내지 않고 null**로 둔다.

### 5.6 검증
- 🔍 단위 테스트 88개 통과, 검증 스크립트 12개 항목 통과 (가상 CoT 10개 → checkpoint 35개)
- ⚠️ **실제 Qwen3 출력으로는 아직 검증하지 않았다.** 정렬 테스트는 가상 텍스트를 다시 토큰화한 합성 ID로만 했다.

### 5.7 회의에서 말할 점
- "실제 출력 몇 개로 checkpoint 경계 토큰과 hidden state 위치를 **A와 함께 직접 확인**해야 한다. 그러려면 **원본 생성 토큰 ID를 그대로** 줘야 한다."
- "Long CoT는 수천 토큰, 문장 수백 개가 될 수 있다. checkpoint마다 강제 답변을 만들면 비용이 문장 수만큼 커진다. 줄이는 방법을 정해야 한다." (9.1절 #8, 10절)

📄 자세히: `docs/checkpoint_report.md`, `docs/qwen3_output_spec.md`

## 6. 작업 보고 ④ STOP/CONTINUE 라벨 (가상 데이터로만 검증)

**목적**: probe가 배울 **정답지**를 만든다.

### 6.1 방법
1. A가 각 checkpoint에서 생각을 끊고 **강제로 답을 내게 한다.**
   (제안 형식: `프롬프트 + <think>\n{prefix}\n</think>\n\n` 뒤에 답을 생성)
2. D&E가 그 답에서 최종 답만 뽑아서 정답과 비교한다.

### 6.2 라벨 규칙

| 상황 | 라벨 | 학습에 사용 |
|---|---|:---:|
| 정규화 EM으로 정답 | **STOP = 1** | ✅ |
| 오답 | **CONTINUE = 0** | ✅ |
| 빈 답, 형식 오류 | 0 + 표시(flag) | ✅ |
| 답이 길이 제한에 걸려 잘림 | EM 결과 + 표시 | ✅ |
| 답변 결과가 아직 없음 | `pending` | ❌ |
| 생성 실패 (error, oom, timeout 등) | `missing` | ❌ |
| 정답을 찾을 수 없음 | `no_reference` | ❌ |

- **checkpoint마다 독립적으로** 판정한다. 예: `[0, 1, 0, 0, 1]` 순서가 그대로 보존된다.
- 여러 번 생성한 결과는 모두 보관하고, **다수결은 하지 않는다.**
- **최종 답만 채점한다.** 생각 속에 정답 단어가 나와도 라벨에 영향이 없다.
- 공식 매칭 결과도 따로 기록한다. 공식 매칭으로만 정답이면 `official_only_match` 표시를 붙인다.

### 6.3 최종 답 추출 규칙 (v1)
1. 마지막 `</think>` 뒤만 사용
2. `<|im_end|>` 같은 특수 토큰 제거
3. 비어 있지 않은 첫 줄만 사용
4. `Answer:`, `The answer is` 같은 머리말 제거
5. `**`, 따옴표, 끝의 마침표 제거

예: `The answer is **two**.` → `two`

### 6.4 동의어 처리
- 공식 정규화 규칙(소문자화, 오타 교정, `2`→`two`, 관사 제거 등) **이외의 동의어 처리는 없다.**
- `sofa`와 `couch`, `left`와 `left side`는 서로 다른 답으로 채점한다.

### 6.5 검증
- 🔍 테스트 29개, 검증 스크립트 10개 항목 통과. 라벨을 독립적으로 다시 채점한 결과와 일치한다.

### 6.6 회의에서 말할 점
- "지금 라벨은 **그 시점의 답이 맞는가**다. 제안서의 **d\***(처음으로 **안정적으로** 맞히기 시작하는 지점부터 STOP)로 바꿀지 결정해야 한다." (9.2절 #10)
- 💭 Long CoT 뒤쪽으로 갈수록 STOP 비율이 높아질 것이다. probe 학습 때 클래스 불균형 가중치를 줄지 A와 이야기해야 한다.

📄 자세히: `docs/labeling_report.md`

## 7. 작업 보고 ⑤ 평가 코드 (가상 데이터로만 검증)

**목적**: "probe로 일찍 멈췄더니 토큰은 얼마나 줄고 정확도는 얼마나 지켰나"를 계산한다.

### 7.1 지표

| 지표 | 계산 |
|---|---|
| **정확도 (주 지표: 정규화 EM)** | 정답 문항 수 / 전체 문항 수 × 100. 공식 매칭(원본 / 빈 답 오답 처리)도 함께 기록 |
| Performance Retention | Early Exit 정확도 / Full CoT 정확도 × 100 |
| Accuracy Difference | Early Exit 정확도 − Full CoT 정확도 (%p) |
| 추론 토큰 감소율 | (Full 평균 추론 토큰 − EE 평균 추론 토큰) / Full 평균 × 100 |
| Latency | total / reasoning / answer / probe 시간의 평균, 중앙값, p90 |
| Probe 품질 | AUROC, AP (τ 없이) / Precision, Recall, F1 (τ 기준) |

- 토큰은 **추론 토큰, 최종 답 토큰, 시험 답 토큰(DEER)** 을 나눠서 기록한다. 라벨을 만들 때 쓴 강제 답변 토큰은 학습 데이터 비용이라 추론 비용과 섞지 않는다.
- 생성에 실패하거나 빈 답이어도 **분모에서 빼지 않고 오답으로 센다.**

### 7.2 평가 모드 (서로 섞지 않음)

| 모드 | 의미 |
|---|---|
| `online` | 실제로 생성을 멈춘 결과. **최종 비교의 기준** |
| `offline_simulation` | "checkpoint k에서 멈췄다면?"을 라벨과 probe 확률로 계산. τ 탐색 같은 보조 용도 |
| `probe_classification` | 멈춤 정책과 상관없는 probe 분류 성능 |

### 7.3 안전장치
- **τ는 validation에서만** 고른다. test가 섞이면 `ThresholdLeakageError`가 나며 멈춘다. 고른 τ는 사용한 문항 목록 해시와 함께 파일로 저장하고 test에는 그대로 쓴다.
- **모든 방식이 같은 문항 집합**이어야 한다. 다르면 오류로 멈춘다.
- 측정하지 않은 값은 숫자를 만들어 넣지 않고 `not_computable`로 표시한다.
- 모든 값에 상태가 붙는다: `measured`(실측) / `estimated`(추정) / `synthetic`(가상) / `undefined`(0으로 나누기 등) / `not_computable`(값 없음)

### 7.4 검증
- 🔍 테스트 30개 통과. 예: EE 정확도가 더 낮은 경우, EE가 토큰을 오히려 더 쓰는 경우, test로 τ를 고르려는 경우, 문항 집합이 다른 경우, Full 정확도가 0인 경우

### 7.5 지금 되는 것과 A의 출력이 있어야 되는 것

| 기능 | 지금 | 필요한 것 |
|---|:---:|---|
| 채점, 정확도, retention | ✅ | 방식별 결과 파일 |
| 최종 답 추출 | ✅ | 실제 Qwen3 출력으로 재확인 |
| 토큰 감소율 (실측) | ⏳ | 원본 생성 토큰 수 |
| Latency | ⏳ | 실제 GPU 측정값 |
| Probe 품질, τ 선정 | ⏳ | probe 예측 |
| 오프라인 시뮬레이션 | ⏳ | 실제 라벨 + probe 확률 |
| 온라인 Early Exit | ⏳ | A가 probe를 생성 루프에 연결 |

### 7.6 회의에서 말할 점
- "온라인 Early Exit 실행과 latency 측정은 누가, 어떤 조건에서 할지 정해야 한다."
- 💭 "오프라인 시뮬레이션과 온라인 결과는 다를 수 있다. 멈춘 뒤 답을 내는 방식이 라벨링 때와 다르면 결과가 달라지기 때문이다. 최종 보고는 온라인 결과로 한다."

📄 자세히: `docs/evaluation_report.md`

## 8. A 담당과 주고받을 파일 형식 (초안)

| 순서 | 파일 | 보내는 쪽 → 받는 쪽 | 핵심 내용 | 명세 |
|---|---|---|---|---|
| 1 | 입력 데이터 `data/processed/sqa3d/*.jsonl` | D&E → A | question_id, 입력(캡션, situation, question) | `preprocessing_report.md` 2절 |
| 2 | Full CoT 생성 결과 `generations_{split}_{run_id}.jsonl` | A → D&E | **원본 생성 토큰 ID**, `generated_text`(가공 없이), 프롬프트 토큰 수, 모델·양자화·생성 설정 | `qwen3_output_spec.md` |
| 3 | checkpoint 파일 | D&E → A | checkpoint_id, prefix, 토큰 위치, hidden_state_position | `checkpoint_report.md` 2.4절 |
| 4 | 강제 답변 `forced_answers_{split}_{run_id}.jsonl` | A → D&E | checkpoint_id, 생성한 답 원문, 생성 상태 | `labeling_evaluation_interface.md` 1절 |
| 5 | 라벨 파일 | D&E → A | STOP/CONTINUE (probe 학습용) | `labeling_report.md` |
| 6 | probe 예측 `probe_predictions_{split}_{version}.jsonl` | A → D&E | checkpoint마다 p_stop (split별 파일 분리) | 인터페이스 4절 |
| 7 | τ 파일 | D&E → A | validation에서 고른 τ (test에 고정 사용) | `evaluation_report.md` 4.6절 |
| 8 | 방식별 결과 `results_{split}_{method}_{run_id}.jsonl` | A → D&E | 최종 답, 실측 토큰 수, latency, 측정 조건 | 인터페이스 5~6절 |

**A에게 꼭 부탁할 것**
1. `generated_text`는 `generated_token_ids`를 `skip_special_tokens=False`로 디코딩한 결과와 **정확히 같아야** 한다. 텍스트를 다시 토큰화해서 ID를 만들면 안 된다.
2. 출력에 strip, 후처리, 답 추출을 하지 않고 **원본 그대로** 준다.
3. A 쪽 파일에는 **정답을 넣지 않는다.** 채점은 D&E가 한다.
4. 생성에 실패한 문항도 **행을 빼지 말고** 상태를 기록해서 준다.
5. 모르는 값은 null로 두고, 추정값이면 `estimated`로 표시한다.

## 10. GPU 비용 감 잡기 (계산 예시 💭)

> 아래는 **결정을 돕기 위한 가정 계산**이다. 실제 값은 Pilot에서 재야 한다.

강제 답변 생성 횟수 = 문항 수 × 문항당 checkpoint 수 × 샘플 수

| 가정 | 문항 수 | 문항당 checkpoint | 샘플 | 강제 답변 횟수 |
|---|---:|---:|---:|---:|
| Long CoT를 문장마다 자름 (문장 100개라고 가정) | 300 | 100 | 1 | **30,000** |
| 짧은 조각을 합치거나 간격을 둬서 20개로 줄임 | 300 | 20 | 1 | **6,000** |
| 처음에 소규모로 먼저 (50문항) | 50 | 20 | 1 | **1,000** |

- 강제 답변은 매번 프롬프트(약 700토큰) + prefix(최대 수천 토큰)를 읽어야 한다. 답은 짧아도 checkpoint가 뒤로 갈수록 입력이 길어진다.
- 여기에 Full CoT 생성(문항당 수천 토큰)과 hidden state 추출 비용이 더해진다.
- 그래서 **checkpoint 개수 줄이기(#8)와 Pilot 범위(#9)를 함께 정해야** 한다.

## 12. 부록

### 12.1 용어 설명

| 용어 | 뜻 |
|---|---|
| CoT (Chain of Thought) | 모델이 답하기 전에 쓰는 생각 과정. Qwen3는 `<think> ... </think>` 안에 쓴다 |
| Long CoT | 수천 토큰에 이르는 긴 생각 과정 |
| hidden state | 모델 내부에서 각 토큰을 읽은 뒤 만들어지는 숫자 벡터. 모델이 "지금 어떤 상태인지"를 담고 있다고 본다 |
| probe | hidden state를 입력받아 STOP/CONTINUE를 예측하는 작은 분류기 (Linear, MLP) |
| checkpoint | 생각을 멈출 수 있는 후보 지점 (예: 문장 끝) |
| prefix | 생각의 처음부터 어떤 checkpoint까지의 누적 텍스트 |
| 강제 답변 (forced answer) | prefix에서 생각을 강제로 끝내고 답을 내게 한 것. 라벨을 만드는 데 쓴다 |
| d\* | 처음으로 안정적으로 정답을 내기 시작하는 지점 (제안서의 "충분한 지점") |
| τ (threshold) | probe의 STOP 확률이 이 값을 넘으면 멈춘다 |
| EM (Exact Match) | 정규화 후 예측과 정답이 완전히 같으면 정답 |
| 정규화 | 소문자화, 특수문자 제거, `2`→`two`, 관사 제거처럼 표기 차이를 없애는 처리 |
| Retention | Full CoT 정확도를 몇 % 유지했는지 |
| AUROC / AP | τ와 상관없이 probe가 STOP과 CONTINUE를 얼마나 잘 구분하는지 (1에 가까울수록 좋음) |
| Precision / Recall / F1 | probe가 STOP이라고 한 것 중 실제 STOP 비율 / 실제 STOP 중 찾아낸 비율 / 둘의 조화평균 |
| Oracle | 정답을 미리 알고 가장 좋은 지점에서 멈추는 상한선. 비교 방식이 아니라 "최대한 잘하면 이만큼"을 보여줌 |
| Pilot | 전체 실험 전에 작은 규모로 먼저 돌려보는 실험 |
| 양자화 | 모델 숫자를 더 적은 비트(4-bit, 8-bit)로 저장해서 메모리를 줄이는 방법. hidden state 값에도 영향을 준다 |
| 데이터 누출 (leakage) | 평가 데이터나 정답 정보가 학습·튜닝에 섞여서 성능이 부풀려지는 것 |
| synthetic (가상) | 코드를 시험하려고 직접 만든 가짜 데이터. 성능 결과가 아님 |

## P2-0. 먼저 큰 그림: 우리 실험을 "시험 채점"에 비유하면

우리 연구를 학생이 시험을 보는 상황에 비유해 보자.

| 실험 | 비유 |
|---|---|
| Qwen3 모델 | 시험을 보는 학생 |
| SQA3D 문제 | 시험 문제 ("내 오른쪽에 있는 냉장고는 무슨 색이야?") |
| 장면 캡션 | 문제에 딸린 지문 (방 안 물건들에 대한 설명) |
| Long CoT (`<think>`) | 학생이 연습장에 쓰는 풀이 과정 |
| checkpoint | 풀이 중간중간 "여기서 답을 써도 될까?" 하고 멈춰 볼 수 있는 지점 |
| 강제 답변 | 그 지점에서 풀이를 멈추게 하고 답을 쓰게 해 보는 것 |
| STOP/CONTINUE 라벨 | 그 지점에서 쓴 답이 맞았는지 (맞았으면 "이제 그만 풀어도 됐다") |
| probe | 학생의 표정(hidden state)만 보고 "이 학생 이제 답 알겠다"를 맞히는 감독관 |
| 평가 | 감독관 말대로 일찍 멈췄을 때 점수는 얼마나 지키고 시간은 얼마나 아꼈는지 |

이 비유에서 **Dataset & Evaluation 담당이 한 일**은 아래와 같다.
- **시험지를 준비**했다: 문제와 지문을 정리하고, 정답지는 따로 보관했다 (①②)
- **풀이 과정을 끊어 볼 지점을 정하는 방법**을 만들었다 (③)
- **채점 기준과 정답지(라벨)를 만드는 방법**을 만들었다 (④)
- **감독관(probe)이 잘했는지 성적표를 내는 방법**을 만들었다 (⑤)

학생에게 실제로 시험을 보게 하는 일(Qwen3 실행)과 감독관을 훈련시키는 일(probe 학습)은 **모델 담당 A**가 맡는다.

## P2-1. 한 문제를 따라가 보기

실제 SQA3D test 문항 하나가 5단계를 어떻게 지나가는지 따라가 보자.
(문제, 상황, 정답은 실제 SQA3D 문항이다. 2단계의 냉장고 캡션과 3단계 이후의 풀이 과정·답·확률은 **설명을 위해 만든 예시**다. 실제 Qwen3 출력이 아니다.)

### 1단계. 원본 문제 (①에서 확인)
```
장면: scene0607_00 (어떤 방의 3D 스캔)
상황(situation): I am facing the paper towel dispenser ...
질문(question): What color is the refrigerator on my right?
정답: brown
```

### 2단계. 모델에 넣을 형태로 바꾸기 (②)
Qwen3는 3D 스캔을 볼 수 없어서, 방 안 물건을 설명하는 문장(캡션) 30개를 대신 넣는다.
```
[장면 설명]  this chair is facing left. it is brown. / a white refrigerator ... / ...
[상황]       I am facing the paper towel dispenser ...
[질문]       What color is the refrigerator on my right?
```
정답 "brown"은 **모델 입력에 절대 들어가지 않고** 채점용으로만 따로 둔다.

### 3단계. 모델이 생각하고 답한다 (A 담당, 예시)
```
<think>
I am facing the paper towel dispenser. The refrigerator should be on my right.
Looking at the captions, there is a refrigerator described as brown.
Wait, let me check the other refrigerator caption.
It also says the refrigerator is next to the counter and is brown.
So the answer is brown.
</think>

brown
```

### 4단계. 풀이 과정을 멈춤 지점으로 자른다 (③)
```
checkpoint 0: (아무 생각도 안 함)
checkpoint 1: "I am facing the paper towel dispenser."
checkpoint 2: + "The refrigerator should be on my right."
checkpoint 3: + "Looking at the captions, there is a refrigerator described as brown."
checkpoint 4: + "Wait, let me check the other refrigerator caption."
checkpoint 5: + "It also says ... is brown."
checkpoint 6: + "So the answer is brown."
```
각 checkpoint는 **처음부터 그 지점까지 누적된 생각**이다.

### 5단계. 각 지점에서 강제로 답하게 하고 채점한다 (A가 답 생성 → ④ 채점)
```
checkpoint 0 → 답 "white"  → 오답 → CONTINUE (0)
checkpoint 1 → 답 "white"  → 오답 → CONTINUE (0)
checkpoint 2 → 답 "white"  → 오답 → CONTINUE (0)
checkpoint 3 → 답 "brown"  → 정답 → STOP (1)   ← 여기서 멈춰도 됐다!
checkpoint 4 → 답 "brown"  → 정답 → STOP (1)
checkpoint 5 → 답 "brown"  → 정답 → STOP (1)
checkpoint 6 → 답 "brown"  → 정답 → STOP (1)
```
이 예시에서는 checkpoint 3에서 이미 답을 알았다. 그 뒤의 생각 3문장은 **없어도 됐던 생각**이다. 이걸 미리 알아채서 줄이는 게 우리 연구의 목표다.

### 6단계. probe가 맞히고, 성적을 낸다 (A가 probe 학습 → ⑤ 평가)
- probe는 각 checkpoint의 hidden state를 보고 "STOP일 확률"을 낸다. 예: 0.1, 0.1, 0.2, **0.7**, 0.8 ...
- 기준값 τ가 0.6이면 checkpoint 3에서 멈춘다. 답은 brown이라 정답이고, 생각 토큰은 절반 가까이 줄어든다.
- ⑤는 이런 결과를 **수천 문제에 대해 모아서** "정확도는 얼마나 지켰고 토큰은 얼마나 줄었는지" 계산한다.

## P2-2. 작업 ① SQA3D 데이터 조사: "시험지가 믿을 만한지 먼저 확인했다"

### 왜 필요했나
데이터를 제대로 알지 못한 채 실험하면, 나중에 결과가 이상해도 원인을 찾을 수 없다. 특히 **정답이 몰래 새어 들어가는 문제(누출)**가 있으면 성능이 부풀려진다. 그래서 실험 전에 데이터를 꼼꼼히 확인했다.

### 무엇을 했나
1. **공식 자료를 확인하고 필요한 파일만 받았다.** 질문·정답 파일(4.6MB)과 장면 설명 캡션 파일만 받았다. 이미지와 비디오(각 400MB 이상)는 텍스트 모델에 필요 없어서 받지 않았다. 받은 파일이 공식 파일과 같은지 지문(md5)으로 확인했다.
2. **문제 수와 나누기를 확인했다.** 학습용(train) 26,623문제, 검증용(val) 3,261문제, 시험용(test) 3,519문제다. 공식적으로 이미 나뉘어 있어서 우리가 새로 나눌 필요가 없다.
3. **같은 방이 여러 세트에 겹치는지 확인했다.** 겹치는 방이 하나도 없었다. 즉 학습 때 본 방이 시험에 나오는 일은 없다.
4. **정답이 어떻게 생겼는지 봤다.** 정답의 93%가 한 단어다(yes, no, left, right, two, brown 등).
5. **공식 채점 방식을 직접 뜯어봤다.** (아래 설명)

### 발견한 중요한 사실 3가지

**(1) 시험 정답이 공개되어 있다**
SQA3D는 test 정답까지 인터넷에 공개되어 있다. 그래서 마음만 먹으면 test 점수를 보면서 설정을 계속 바꿀 수 있다. 이건 시험 문제를 미리 보고 공부하는 것과 같다. 그래서 **"모든 조정은 val로만 하고, test는 맨 마지막에 딱 한 번만 본다"** 는 규칙을 정했다. ⑤의 평가 코드는 이 규칙을 어기면 에러가 나도록 만들었다.

**(2) 공식 채점이 너무 너그럽다**
공식 채점 코드는 예측과 정답이 **단어 하나만 겹쳐도 정답**으로 친다.
- 정답 "left side", 예측 "right side" → "side"가 겹쳐서 **정답** 처리
- 예측이 **빈칸**이어도 정답 처리 (프로그램 특성상 빈 문자열은 무엇에든 포함되는 것으로 판단됨)

원저자도 "조금 공격적인(aggressive) 채점"이라고 인정했다.
우리 연구에서는 이게 특히 위험하다. 라벨(STOP/CONTINUE)이 채점 결과로 정해지기 때문이다. 채점이 너그러우면 "아직 답을 모르는데 맞았다고 판정 → 너무 일찍 STOP"이 된다. 그래서 **정규화 EM**(표기만 맞춘 뒤 완전히 같아야 정답)을 주 기준으로 쓰고, 공식 점수는 다른 논문과 비교하기 위해 함께 적는다.

**(3) 질문만 봐도 꽤 맞힐 수 있다**
공식 리더보드에서 3D 정보를 아예 안 준 모델(Blind)이 43.65점, 3D를 보는 모델(ScanQA)이 46.58점이다. 차이가 크지 않다. 질문 패턴과 정답이 한쪽으로 쏠려 있어서 그렇다(예: "Is ...?" 질문은 yes/no). 그래서 우리도 **"캡션 없이 질문만 줬을 때" 점수**를 함께 재야, 모델이 정말 장면 설명을 활용했는지 보여줄 수 있다.

### 그 밖에 발견한 것
- **정답이 서로 다른 같은 문제 5개**: 위치와 방향까지 똑같은 문제인데 정답이 다르다. 예: "욕조는 무슨 색이야?" → 한쪽 정답은 `brown`, 다른 쪽은 `backward`(다른 문제 정답이 섞인 것으로 보임).
- **모델이 이미 봤을 가능성**: 정답이 몇 년째 공개되어 있어서 Qwen3가 학습 중에 봤을 수도 있다. 확인할 방법이 없어서 보고서에 한계로 적는 것을 제안한다.

### 팀원이 알아야 할 것
- test 결과는 **마지막에 한 번만** 본다. 중간에 test 점수를 보고 뭔가를 바꾸면 안 된다.
- 다른 논문의 SQA3D 점수(공식 채점)와 우리 EM 점수는 기준이 달라서 **직접 비교하면 안 된다.** 비교할 때는 우리가 함께 기록한 공식 점수를 쓴다.

## P2-3. 작업 ② 전처리, 분할, Pilot: "시험지를 모델이 읽을 수 있는 형태로 만들었다"

### 왜 필요했나
원본 데이터는 질문 파일과 정답 파일이 따로 있고, 장면 설명은 또 다른 파일에 있다. 매번 이걸 합치면 사람마다 다르게 합칠 수 있다. 그래서 **누가 돌려도 똑같이 나오는 하나의 입력 파일**을 만들었다.

### 무엇을 했나

**(1) 한 문제를 한 줄로 정리했다**
한 줄에 문제 번호, 모델이 읽을 내용(장면 설명, 상황, 질문), 정답, 기타 정보가 들어 있다. 핵심은 **모델이 읽을 칸(`input`)과 정답 칸(`reference_answers`)을 완전히 분리**한 것이다. 모델에 들어가는 건 `input` 안의 내용뿐이다.

**(2) 3D 장면을 글로 바꿨다**
Qwen3는 글만 읽는다. 그래서 방 안 물건을 설명한 문장(ScanRefer 캡션)을 넣는다. 예: "a black tv, ... on the right side of the blue curtain". 이건 SQA3D 공식 LLM 평가 방식과 같다.
- 방마다 캡션이 보통 60개쯤(중앙값) 있는데, 공식 방식처럼 **30개만** 쓴다.
- 공식 코드는 30개를 매번 무작위로 뽑아서, 돌릴 때마다 입력이 달라진다. 우리는 **방마다 고정된 방식으로 뽑아서** 누가 언제 돌려도 같은 30개가 들어가게 했다. 같은 방의 모든 문제에는 같은 30개가 들어간다.

**(3) 문제를 하나도 지우지 않았다**
이상한 문제가 있어도 지우지 않고 **표시(flag)만** 했다. 나중에 "어떤 문제를 뺐는지"를 팀이 정할 수 있게 하기 위해서다. 원본 파일도 전혀 건드리지 않았다.

**(4) 작은 연습용 세트(Pilot)를 만들었다**
Long CoT는 문제 하나에도 GPU 시간이 많이 든다. 그래서 전체 3만 문제 전에 **train 300 / val 100 / test 100문제**로 먼저 실험해 볼 수 있게 했다.
- 아무렇게나 뽑으면 특정 유형의 문제만 몰릴 수 있다. 그래서 **질문 종류(What/Is/How...) × 정답 종류(예·아니오/숫자/방향/색/기타)** 비율이 전체와 같아지도록 뽑았다. 실제로 비율이 거의 같다(예: What 질문 비율 30.7% → Pilot 30.7%).
- 이상한 문제(캡션 없음, 정답 충돌, 중복)는 Pilot에서 뺐다.

**(5) 입력 길이를 쟀다**
Qwen3의 tokenizer(글을 토큰으로 자르는 도구)만 CPU에서 써서 셌다. 입력은 보통 약 700토큰, 가장 긴 것도 약 1,100토큰이다. 입력은 짧은 편이라, 메모리 부담은 주로 **모델이 길게 생각하는 출력 쪽**에서 생길 것으로 본다.

### 어떻게 검증했나
- **59가지 항목을 자동으로 검사**해서 모두 통과했다. 예: 문제 수가 원본과 같은지, 문제 번호가 겹치지 않는지, 세트 사이에 방이 겹치지 않는지, 정답이 빠진 문제가 없는지.
- **정답이 새지 않는지 검사**: 정답 칸을 일부러 엉뚱한 글자로 바꿔 놓고 모델 입력을 다시 만들어 봤다. 3만 3천여 문제 모두 입력이 **전과 똑같았다.** 즉 입력을 만드는 코드는 정답을 전혀 읽지 않는다.
- **재현성 검사**: 두 번 돌려서 나온 파일이 완전히 같았다.

### 팀이 정해야 할 것
- 캡션이 아예 없는 방 2개(train 1개 50문제, val 1개 49문제)를 어떻게 할지. 추천은 학습·주 평가에서 빼고 몇 개 뺐는지 적는 것이다.
- 지금 프롬프트(모델에게 주는 지시문)는 **임시**다. Qwen3 thinking 모드에 맞게 A와 함께 정하면 바꾸고 길이를 다시 잴 것이다.

### 팀원이 알아야 할 것
- 실험 입력은 `data/processed/sqa3d/` 파일을 그대로 쓰면 된다. 직접 원본을 다시 합치지 않는다.
- 데이터 파일은 용량 때문에 GitHub에 올라가지 않는다. 스크립트로 다시 만들 수 있다.

## P2-4. 작업 ③ Reasoning Checkpoint: "풀이 과정을 멈춰 볼 지점으로 잘랐다"

### 왜 필요했나
probe는 "지금 멈춰도 될까?"를 판단한다. 그러려면 **"지금"이 언제인지**, 즉 판단할 지점들이 정해져 있어야 한다. 모든 토큰마다 판단하면 너무 많으니, **문장이 끝나는 곳** 같은 자연스러운 지점에서만 판단하기로 했다.

### 무엇을 했나

**(1) 생각과 답을 분리한다**
Qwen3는 `<think>` 생각 `</think>` 답 형태로 출력한다. 이걸 나눈다. 실제 출력은 항상 깔끔하지 않으므로, 형식이 이상해도 멈추지 않고 어떤 상태인지 기록한다.
- 정상 / 여는 태그 없음 / 생각하다가 잘림 / 태그가 아예 없음 / 생각이 비어 있음 / 출력 자체가 비어 있음

**(2) 생각을 조각으로 자른다 (방법 3가지)**
- **문장 단위 (기본)**: 마침표·물음표·느낌표 뒤, 줄바꿈에서 자른다. 단, `3.5 m` 같은 소수점, `e.g.` 같은 약어, 줄 앞의 `1.` 같은 번호에서는 자르지 않는다.
- **줄 단위**: 줄이 바뀔 때마다
- **번호 단위**: `1.`, `Step 2:`처럼 단계 번호가 붙은 곳에서

잘린 조각을 다시 이어 붙이면 **원래 글과 한 글자도 다르지 않은지** 테스트로 확인했다.

**(3) 각 지점까지의 누적 생각(prefix)을 만든다**
checkpoint 3의 prefix는 "1번 문장 + 2번 문장 + 3번 문장"이다. 강제 답변은 이 prefix를 보고 답을 내게 된다.

**(4) Checkpoint 0 = "아무 생각도 안 한 상태"**
생각 없이 바로 답하면 어떻게 되는지도 봐야 한다. 그게 비교 기준(Direct Answer)이 되기 때문이다.

**(5) hidden state를 꺼낼 위치를 계산한다**
probe는 각 지점의 **마지막 토큰을 읽은 직후의 hidden state**를 본다. 그래서 각 checkpoint가 전체 토큰 중 몇 번째에서 끝나는지 계산한다.
```
hidden state 위치 = 프롬프트 토큰 수 + 생각 속 끝 위치 - 1
```

### 만들면서 발견하고 고친 문제
Qwen3 tokenizer는 **띄어쓰기를 다음 단어에 붙인다.** "... the door. So the ..."에서 `" So"`(앞 공백 포함)가 한 토큰이 된다.
처음에는 checkpoint의 끝을 "공백까지 포함한 위치"로 잡았다. 그랬더니 마지막 토큰이 다음 문장 첫 단어 `" So"`가 되어, probe가 **다음 문장을 살짝 엿본 상태**의 hidden state를 보게 되는 문제가 있었다. 시험으로 치면 다음 줄을 커닝한 셈이다.
→ **공백을 뺀 위치**를 기준으로 맞추도록 고쳤다. 이제 마지막 토큰은 항상 그 문장의 마침표다.

### 지어내지 않는 원칙
토큰 위치는 **모델이 실제로 만든 토큰 번호(ID)가 있을 때만** 계산한다. 없으면 빈칸(null)으로 둔다. 글을 다시 토큰으로 잘라서 계산하면 실제 생성과 달라질 수 있어서, 틀린 위치를 그럴듯하게 채우는 것보다 비워 두는 게 낫다고 판단했다.

### 어떻게 검증했나
- 가상 풀이 10개로 테스트 88개를 만들어 모두 통과했다. 예: 소수점에서 안 자르는지, 생각이 비었을 때, 태그가 빠졌을 때, 정답을 넣어도 결과가 안 바뀌는지.
- ⚠️ **실제 Qwen3 출력으로는 아직 확인하지 못했다.** 실제 출력이 오면 몇 개를 골라 A와 함께 위치가 맞는지 직접 확인해야 한다.

### 팀이 정해야 할 것
Long CoT는 문장이 수백 개일 수 있다. 문장마다 강제 답변을 만들면 GPU 비용이 너무 크다. 그래서 **짧은 문장 합치기 / 몇 문장 간격으로만 보기 / "Wait," 같은 생각 전환 지점에서 자르기** 중 방법을 정해야 한다. 코드는 새 방법을 쉽게 추가할 수 있게 만들어 두었다.

### 팀원(특히 A)이 알아야 할 것
- 생성 결과를 줄 때 **모델이 만든 토큰 번호를 그대로** 같이 줘야 한다. 글만 주면 hidden state 위치를 정확히 잡을 수 없다.
- 출력 글은 다듬지 말고 **원본 그대로** 줘야 한다.

## P2-5. 작업 ④ STOP/CONTINUE 라벨: "probe가 배울 정답지를 만드는 규칙을 만들었다"

### 왜 필요했나
probe는 "지금 멈춰도 되는가"를 배워야 한다. 배우려면 **각 지점마다 정답(멈춰도 됐다 / 더 생각해야 했다)** 이 있어야 한다. 이 정답지를 라벨이라고 한다.

### 어떻게 라벨을 정하나
1. A가 각 checkpoint에서 생각을 강제로 끝내고 답을 내게 한다.
2. 그 출력에서 **최종 답만** 뽑는다.
3. 정답과 비교한다(정규화 EM).
   - 맞으면 **STOP (1)** = "여기서 멈춰도 정답을 낼 수 있었다"
   - 틀리면 **CONTINUE (0)** = "더 생각해야 했다"

### 최종 답은 어떻게 뽑나
모델은 "The answer is **two**." 처럼 답을 꾸며서 쓸 수 있다. 그래서 정해진 순서로 다듬는다.
1. `</think>` 뒤만 본다 (생각 속 내용은 채점하지 않는다)
2. 끝을 알리는 특수 기호(`<|im_end|>` 등)를 지운다
3. 첫 줄만 남긴다
4. "Answer:", "The answer is" 같은 머리말을 지운다
5. 굵은 글씨 기호, 따옴표, 끝의 마침표를 지운다

→ `The answer is **two**.` 가 `two`가 된다.

### 정규화 EM이 하는 일
표기 차이만 없앤다: 대문자→소문자, `2`→`two`, 관사(the, a) 제거, 흔한 오타 교정(`letf`→`left`) 등. 이건 공식 SQA3D 규칙을 그대로 쓴 것이다.
**뜻이 같은 다른 단어(동의어)는 맞다고 보지 않는다.** `sofa`와 `couch`는 다른 답이다. 동의어를 마음대로 늘리면 채점이 사람마다 달라지기 때문이다.

### 애매한 경우 처리

| 상황 | 처리 | 이유 |
|---|---|---|
| 답이 빈칸이거나 형식이 이상함 | CONTINUE(0) + 표시 | 정답을 내지 못한 것이므로 |
| A가 아직 답을 만들지 않은 지점 | `pending` (학습 제외) | 모르는 것을 틀렸다고 하면 안 되므로 |
| 생성하다 오류가 난 지점 | `missing` (학습 제외) | 모델 실력이 아니라 실행 문제이므로 |
| 같은 지점에서 여러 번 답을 만든 경우 | 모두 따로 보관, 다수결 안 함 | 정보를 버리지 않고 나중에 방법을 정하려고 |

- **지점마다 따로 판정한다.** 앞에서 맞혔다가 뒤에서 다시 틀리는 경우(예: `0, 1, 0, 0, 1`)도 그대로 기록한다. 실제로 모델은 "Wait," 하면서 맞는 답을 버리기도 한다.
- 공식 채점으로는 맞고 EM으로는 틀린 경우(예: "not left" vs "left")는 따로 표시해서 나중에 분석할 수 있게 했다.

### 어떻게 검증했나
가상 데이터로 여러 시나리오를 만들어 확인했다: 모두 정답, 모두 오답, 중간부터 정답, 맞혔다가 다시 틀림, 마지막에만 정답, 답이 없음, 여러 번 생성. 테스트 29개, 검증 10개 항목 모두 통과했다.

### 팀이 정해야 할 것: 라벨 정의
- **지금 방식 (a)**: "그 지점에서 답이 맞았는가"
- **제안서 방식 (b) d\***: "처음으로 **계속** 맞히기 시작하는 지점부터 STOP"
  예: `0, 1, 0, 1, 1` → (a)는 2번째도 STOP이지만, (b)는 2번째 뒤에 다시 틀리므로 4번째부터 STOP
- (b)가 더 엄격하고 안전하다. 추천은 두 가지 다 계산해서 비교하는 것이다. 지금 데이터로 (b)도 계산할 수 있다.

## P2-6. 작업 ⑤ 평가 코드: "일찍 멈춘 효과를 공정하게 재는 성적표를 만들었다"

### 왜 필요했나
"우리 방법이 좋다"고 말하려면 **같은 기준으로 공정하게** 비교해야 한다. 비교 방법이 조금만 달라도 결과가 쉽게 부풀려진다. 그래서 숫자를 계산하는 규칙과 실수를 막는 장치를 미리 만들었다.

### 무엇을 비교하나
| 방식 | 설명 |
|---|---|
| Direct Answer | 생각 없이 바로 답 |
| Fixed-k | 무조건 k문장(또는 정해진 토큰 수)만 생각하고 답 |
| Full Long CoT | 끝까지 다 생각하고 답 (기준) |
| **Probe Early Exit** | probe가 "이제 됐다"고 하면 멈추고 답 (우리 방법) |
| DEER 방식 | 중간중간 시험 삼아 답을 내 보고 멈출지 결정 |
| Oracle | 정답을 알고 가장 이른 곳에서 멈춤 (이론상 최고치) |

### 어떤 숫자를 내나 (쉬운 설명)
| 지표 | 쉬운 뜻 | 예시 |
|---|---|---|
| 정확도 | 100문제 중 몇 개 맞혔나 | 60% |
| Retention | 끝까지 생각했을 때 점수의 몇 %를 지켰나 | Full 60%, 우리 57% → 95% 유지 |
| 정확도 차이 | 끝까지 생각했을 때보다 몇 점 떨어졌나 | −3%p |
| 토큰 감소율 | 생각 길이를 몇 % 줄였나 | 2,000 → 1,200토큰이면 40% 감소 |
| Latency | 실제로 시간이 얼마나 걸렸나 | 문제당 평균 몇 초 |
| Probe 품질 (AUROC 등) | probe가 STOP/CONTINUE를 얼마나 잘 맞히나 | 1에 가까울수록 좋음 |

(위 예시 숫자는 설명용이다. 실제 결과가 아니다.)

### 공정하게 비교하기 위한 안전장치
1. **τ(멈추는 기준값)는 val에서만 고른다.** test로 고르면 에러가 나며 멈춘다. 고른 τ는 파일로 저장해서 test에 그대로 쓴다.
2. **모든 방식을 같은 문제들로 비교한다.** 어떤 방식만 쉬운 문제로 평가되면 안 되므로, 문제 목록이 다르면 에러가 난다.
3. **실패한 문제도 빼지 않는다.** 생성에 실패하거나 답이 비면 오답으로 센다. 실패한 문제를 빼면 점수가 부풀려지기 때문이다.
4. **재지 않은 값은 지어내지 않는다.** 토큰 수나 시간이 기록되지 않았으면 "계산할 수 없음(`not_computable`)"으로 표시한다.
5. **값마다 출처 표시가 붙는다.** 실측(`measured`) / 추정(`estimated`) / 가상(`synthetic`)이 구분되어서, 가상 숫자가 실제 결과로 오해받지 않는다.
6. **비용을 섞지 않는다.** 실제 추론에 쓴 토큰, DEER처럼 시험 삼아 낸 답의 토큰, 라벨을 만들려고 쓴 토큰을 따로 센다.

### 평가하는 3가지 방법 (섞지 않음)
- **실제 실행 (online)**: 진짜로 생성을 멈춰 본 결과. **최종 결과는 이걸로 보고한다.**
- **시뮬레이션 (offline)**: "k번째에서 멈췄다면?"을 이미 만든 라벨로 계산. 빠르게 τ를 찾아볼 때 쓴다.
- **probe 분류 성능**: probe가 라벨을 얼마나 잘 맞히는지만 본다.

### 어떻게 검증했나
가상 데이터로 일부러 까다로운 상황을 만들어 테스트 30개를 통과했다. 예: 우리 방법이 오히려 점수가 낮은 경우, 오히려 토큰을 더 쓴 경우, test로 τ를 고르려는 경우, 비교 문제 목록이 다른 경우, 기준 점수가 0이라 나눗셈이 안 되는 경우.

### 팀원이 알아야 할 것
- 지금 코드에서 나오는 숫자(예: 토큰 49% 감소)는 **가상 데이터라 의미가 없다.** 발표나 보고서에 쓰면 안 된다.
- 실제 숫자는 A의 실험 결과 파일이 들어오면 같은 코드로 바로 계산할 수 있다.

## P2-7. 팀원들이 물어볼 만한 질문 (Q&A)

**Q1. 그럼 지금 실제로 나온 실험 결과는 있나요?**
아직 없다. 실제 데이터로 끝낸 건 ①②(데이터 준비)까지다. ③④⑤는 코드를 완성하고 가상 데이터로 제대로 동작하는지만 확인했다. 실제 결과는 A가 Qwen3를 돌린 뒤에 나온다.

**Q2. 왜 공식 채점을 안 쓰고 EM을 쓰나요?**
공식 채점은 단어 하나만 겹치거나 답이 빈칸이어도 정답으로 친다. 라벨이 채점으로 정해지는 우리 연구에서는 "모르는데 맞았다"가 많아져서 probe가 너무 일찍 멈추도록 배우게 된다. 다른 논문과 비교할 수 있도록 공식 점수도 함께 기록한다.

**Q3. 왜 캡션을 30개만 쓰나요? 전부 넣으면 안 되나요?**
공식 LLM 평가 방식이 30개다. 전부 넣어도 최대 약 5,200토큰이라 들어가긴 하지만, Long CoT까지 더하면 16GB GPU에서 메모리와 시간 부담이 커진다. 바꾸고 싶으면 팀에서 정하면 된다.

**Q4. 캡션 30개를 고정한 게 공식 방식과 다르지 않나요?**
공식 코드는 seed 없이 매번 무작위로 뽑아서 재현이 안 된다. 우리는 같은 30개 규칙(무작위 30개)을 따르되, 누가 돌려도 같은 결과가 나오게 고정했다. 보고서에 이 차이를 적으면 된다.

**Q5. Pilot은 왜 필요한가요?**
Long CoT는 문제 하나에 수천 토큰을 생성하고, 라벨을 만들려면 지점마다 답을 또 생성해야 한다. 바로 3만 문제를 돌리면 시간이 얼마나 걸릴지, 설정이 맞는지 모르는 채 GPU를 오래 쓰게 된다. 작은 세트로 먼저 문제를 찾고 시간을 잰다.

**Q6. hidden state 위치가 왜 그렇게 중요한가요?**
probe는 그 위치의 hidden state만 보고 판단한다. 위치가 한 칸만 밀려도 "다음 문장을 엿본 상태"나 "아직 문장을 다 안 읽은 상태"를 보게 된다. 그러면 probe 결과를 믿을 수 없다. 그래서 A에게 토큰 번호 원본을 꼭 달라고 요청하는 것이다.

**Q7. 라벨에서 앞에서 맞혔다가 뒤에서 틀리는 경우가 실제로 있나요?**
Long CoT 모델은 "Wait, actually..." 하면서 맞는 답을 버리고 다른 답으로 가기도 한다. 그래서 지점마다 따로 판정하고, d\* 방식을 쓸지는 팀에서 정하기로 했다.

**Q8. 이 코드는 어디서 볼 수 있나요?**
아직 GitHub에 올리지 않았다. 회의에서 올리는 방식을 정하면 새 브랜치로 올리고 PR 링크를 공유하겠다. 데이터 파일은 용량 때문에 올라가지 않고 스크립트로 다시 만든다.

## P2-8. 한 장 요약: 내가 넘겨줄 것과 받아야 할 것

**내가 이미 준비한 것 (A가 바로 쓸 수 있음)**
- 모델 입력 파일: 전체 train / val / test + Pilot 300 / 100 / 100
- 출력 형식 명세: `qwen3_output_spec.md`, `labeling_evaluation_interface.md`
- 출력이 오면 바로 돌릴 코드: checkpoint 분할 → 라벨 → 평가

**A에게 받아야 하는 것**
1. Full Long CoT 생성 결과 (**토큰 번호 원본** 포함)
2. checkpoint마다 강제로 낸 답
3. probe 예측 확률 (train / val / test 파일 따로)
4. 방식별 실제 실행 결과 (토큰 수, 시간 포함)

**그다음 내가 할 것**
1. 실제 출력으로 checkpoint 위치가 맞는지 A와 함께 확인
2. 실제 라벨 만들기 → A에게 전달 (probe 학습용)
3. val로 τ 고르기 → test 한 번 평가 → 최종 결과표
